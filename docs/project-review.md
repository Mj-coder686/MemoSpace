# MemoSpace 项目复盘与面试说明

## 为什么 Memory 和 Space 是多对多？

一条“西安旅行”记忆天然既属于用户的私人记忆库，也可能出现在情侣空间、家庭空间或事件页中。如果复制 Memory 主体，修改标题、权限或删除媒体时就会出现多份数据不一致。项目因此让 `memory` 保存唯一事实，用 `memory_space` 表示投影位置。同步到空间只是增加关联，不复制内容。

## 情侣 / 好友权限如何保证？

JWT 只负责回答“当前是谁”，不能证明“可以看什么”。每次空间和 Memory 操作都进入 `PermissionService`：空间访问检查 `space_member`；关系可见 Memory 检查其关联空间中是否存在当前成员；编辑和删除仍只允许创建者。前端隐藏按钮只是体验优化，后端是最终边界。

## 关系解除后数据如何处理？

关系与空间状态改为 `ARCHIVED`，记录 `archived_at`。空间成员仍能读取当时有权访问的历史，但 `canUploadToSpace` 要求空间为 `ACTIVE`，因此不能再添加内容。Memory 主体仍在个人库中，避免关系变化抹掉个人历史。

## 为什么公共 Post 和 Memory 分开？

Memory 是私人历史，Post 是一次公开发布行为。两者的生命周期不同：Memory 可能长期存在但暂时不公开；Post 将来还会有推荐状态、审核、发布时间、分享策略。分开后撤回公开只删除/停用 Post，不需要破坏 Memory。

## 私有照片如何保护？

上传时用文件魔数识别 MIME，不信任扩展名；对象键由用户 ID、日期和 UUID 生成；本地存储路径规范化后检查不能越出根目录。文件下载先检查拥有者或关联 Memory 的访问权限。MinIO bucket 保持私有，只返回 10 分钟有效的签名地址，不在数据库保存永久公网 URL。

## Redis 用在哪里？

V1 用 Redis 缓存公共 Feed，数据库仍是事实来源。Feed 只缓存两分钟，发布或修改内容时递增版本号完成 O(1) 失效，避免生产环境使用 `KEYS` 扫描。Redis 故障会自动回退数据库，不阻塞发布。用户/空间缓存、验证码和实时通知会在数据规模需要时按相同原则增加，不缓存所有数据。

## 关系邀请如何防并发？

应用先检查自我邀请、重复待处理邀请和已有关系；接受邀请在事务内对邀请行执行 `FOR UPDATE`，再次检查状态和过期时间，再创建 relationship、成员和空间。单实例创建邀请还使用同步临界区。多实例生产版应再增加数据库唯一约束/规范化关系对键，或使用 Redis 分布式锁作为辅助，但最终一致性仍由数据库约束承担。

## 如何防越权？

不接受前端传入的 creator ID；所有创建者取自 JWT。关系邀请只允许 receiver 响应；文件必须属于上传者才能挂载；事件和空间写入都先检查成员和空间状态；Memory 读取、修改、删除分别进入统一权限方法。集成测试专门使用另一用户 Token 请求私人 Memory，期望 403。

## 如果有 100 万用户怎么办？

保持单体但可以水平扩容无状态 API：JWT 不依赖本机 Session；媒体直传对象存储；MySQL 对用户、时间、空间关联建立复合索引并按时间归档；热点 Feed 使用 Redis；图片处理通过队列异步化。数据量继续增长时优先按用户或时间对 Memory 分区，而不是先拆业务微服务。

## Feed 如何优化？

V1 使用时间倒序和关注关系过滤。下一步改为 `(published_at,id)` 游标分页，避免深 offset；关注 Feed 可从读时聚合过渡到大多数用户写扩散、超级用户读扩散的混合策略；Redis 只缓存短窗口结果和计数。推荐算法与关注 Feed 保持独立。

## 图片特别多以后怎么办？

原图保存在对象存储，数据库只存对象键和元数据；上传后异步生成多尺寸 WebP/AVIF 与模糊占位图；前端按视口选择尺寸、懒加载并使用 CDN。相册查询基于 occurred_at、space_id 和人物标签分页，不扫描对象存储。对象生命周期策略将冷数据迁移到低频存储。

## 重要取舍

- V1 保持模块化单体，降低关系权限的分布式一致性成本。
- 本地默认 H2/本地文件让项目开箱即用，Docker profile 才启用 MySQL、Redis 和 MinIO。
- UI 使用统一 Design Tokens 和 CSS Variables，不为每种关系复制样式。
- AI 与 WebSocket 属于 V2/V3，不让高级能力推迟首条完整用户路径。

# V1.1 产品修复与验收记录

## 媒体根因与修复

原实现只在 Memory 详情返回媒体，列表卡片拿不到真实文件 ID，因此始终展示装饰性占位封面。详情媒体又通过带 JWT 的 XHR 请求后端，再由后端 `302` 到 `MINIO_PUBLIC_ENDPOINT` 生成的 presigned URL；这条跨源重定向链依赖主机地址和 MinIO CORS，导致数据库和对象都存在时浏览器仍可能无法取得 Blob。

V1.1 做了两处结构性修复：

1. Memory 列表、首页、Feed 与关系空间时间轴返回首个 `cover_file_id` 和 `cover_mime_type`，前端在有媒体记录时加载真实文件，不用占位图掩盖错误。
2. `/api/files/{id}/content` 先按 PRIVATE / PUBLIC / RELATIONSHIP 权限校验，再由后端从私有 MinIO bucket 流式返回媒体；移除 presigned 重定向和 `MINIO_PUBLIC_ENDPOINT` 依赖。

## 自动化验收

后端：

```bash
cd backend
mvn test
```

当前共 5 个集成测试，覆盖关系邀请接受/拒绝、关系建立与封存、分类多标签单空间、隐藏/恢复、真实 PNG 字节和媒体越权矩阵。

浏览器：

```bash
cd frontend
npx playwright test e2e/v11-full-journey.spec.ts
```

Playwright 使用系统 Chrome 与三个隔离账号，执行：注册 → A 搜索 B → 选择“恋人”并邀请 → B 接受 → A 在分类中看到 B → 进入唯一共同空间 → 创建自定义标签并验证仍指向同一空间 → 分别上传 PUBLIC、PRIVATE、RELATIONSHIP 图片 → 验证图片 `naturalWidth > 0` → 校验三账号的 Memory/文件访问矩阵 → 隐藏分类 → 验证空间与媒体仍存在 → 恢复分类并确认原空间重新出现。

最近一次通过证据位于 `frontend/test-results/v11-artifacts/`，包括 7 张阶段截图和 `v11-evidence.json`。该次运行验证了 18 组 Memory/文件 HTTP 状态：合法读取为 `200 image/png`，越权读取为 `403 application/json`。
